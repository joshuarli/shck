# Linting

The lint engine lives in `shuck-linter`. Rules read precomputed facts, report diagnostics, and optionally attach fixes. The CLI builds settings and invokes `shuck_linter::analyze` or `shuck_linter::lint`.

## Rules and categories

Rule codes are a category letter plus a number.

| Category | Prefix | Default |
| --- | --- | --- |
| Correctness | `C` | on |
| Style | `S` | off |
| Performance | `P` | on |
| Portability | `X` | on |
| Security | `K` | on |

Shuck also accepts ShellCheck codes (`SC2086`, `2086`) in selectors and suppression directives when a rule maps to one. Legacy `SH-NNN` codes are suppression aliases only; selectors reject them.

The registry is generated by `declare_rules!` in `crates/shuck-linter/src/registry.rs`. It owns the `Rule` enum, `Rule::iter()`, `Rule::code`, `Rule::category`, and default severities. Codes are unique and `Rule::COUNT` matches the table; tests enforce both. Rule metadata (`description`, `rationale`, `fix_description`, ShellCheck level and aliases) is generated by the build script from `docs/rules/*.yaml`.

The YAML files under `docs/rules/` are inputs to the build and to parity tests, not generated output. A rule change updates its spec there.

## Selection and defaults

Selectors parse as `ALL`, a named group, an exact rule code, a category letter, or a code prefix. `apply_rule_selector_layer` applies selectors in ascending specificity, so `C` followed by `C001` leaves `C001` selected; `ignore` removes rules after selection. Selectors from config and CLI merge through `SettingsResolver`.

`LinterSettings::default_rules()` enables every non-style rule except `C158`, `C159`, `C160`, and `C161`. The named group `google` currently selects 17 ShellCheck-aligned rules; it does not include the newer Google-style rules described below. `RuleSet` is a fixed bitset, and settings are part of the check cache key.

## Checker dispatch

`Checker::check()` returns immediately when no rules are enabled. Otherwise it runs these phases in order:

1. bindings
2. references
3. scopes
4. declarations
5. call sites
6. source references
7. command facts
8. word and expansion facts
9. loop, list, and pipeline facts
10. redirect and substitution facts
11. surface-fragment facts
12. test and conditional facts
13. flow and file policy

Each phase is a flat list of `is_rule_enabled` checks that call a rule module with the checker. Iteration over commands, words, and other entities happens inside facts or the rule module, not in the phase dispatcher.

The semantic pass exposes an observer (`TraversalObserver`) used by `LintTraversalObserver` to record command visits, conditional-expression visits, and statement-sequence commands once. Facts and suppressions consume those records, so rules do not re-walk the AST.

## Facts and rule authoring

`LinterFacts` is built once per file and owns reusable structural summaries: command facts with packed child lists, word and expansion facts, assignment facts, source facts, and compatibility facts. View types such as `CommandFacts`, `WordFacts`, and `SourceFacts` are the public surface; the stores behind them are private.

Rule files must stay cheap filters over facts plus policy and wording. They must not add direct AST walks, call traversal helpers, or import `crate::rules::common::*`. If a rule needs new structural information, add it to `crates/shuck-linter/src/facts/` and expose it through the facts views. `CommandTopology` is the authoritative command tree for facts. An architecture test rejects direct AST traversal tokens in rule files, with one allowlisted debt file.

The linter crate enforces `clippy::wildcard_enum_match_arm` on the rule modules so new enum variants force an explicit decision.

See `crates/shuck-linter/AGENTS.md` for the crate-level layering rules.

## Diagnostics and fixes

`Diagnostic` carries a rule, message, severity, span, optional `Fix`, and optional fix title. `Severity` is `Hint`, `Warning`, or `Error`; default severity comes from the rule table. Rules implement `Violation` (`rule`, `message`, `fix_title`, `FIX_AVAILABILITY`) and report through the checker, which deduplicates by rule and span.

Fixes are `Fix { edits, applicability }` with `Safe` or `Unsafe` applicability. `apply_fixes` skips overlapping edits. `shuck check --fix` applies safe fixes; `--unsafe-fixes` also applies unsafe ones. Fix availability is checked against `docs/rules/*.yaml`.

Final diagnostic order is: apply severity overrides, filter suppressions, filter per-file ignores, then sort by span start and end. Parse diagnostics are collected with the same rule surface and sanitized when the parse failed.

## Suppressions

Suppression directives are parsed from comments by `crates/shuck-linter/src/suppression/`:

- `# shuck: disable=C001,S001` suppresses the next command; before the first statement it becomes file-wide.
- `# shuck: disable-file=S001` suppresses the whole file anywhere.
- `# shuck: ignore=C001` suppresses diagnostics on the directive's own line.
- `# shellcheck disable=SC2086` uses ShellCheck scope rules and accepts native codes too.

Both syntaxes accept either code namespace; unmapped ShellCheck codes are dropped. `disable` directives attach to the next command span from the semantic pass. Inline `disable` comments are kept when they attach to a following command or a compound header; `ignore` and `disable-file` are never filtered. `SuppressionIndex` stores a whole-file flag, ignored lines, and command line ranges per rule. `--add-ignore` inserts `# shuck: ignore=` directives, re-analyzes each target line, and accepts the edit only when it removes exactly that line's diagnostics.

## Expansion analysis

Expansion facts answer context-sensitive questions about words. The layer has three parts:

1. **Context.** `ExpansionContext` enumerates command name, argument, assignment value, declaration value, redirect target, descriptor duplication, here-string, `for`/`select` list, case pattern, conditional pattern, string-test operand, regex, subscript, parameter pattern, and trap action. Words are also classified by host shape, such as direct, wrapper target, or subscript.
2. **Word analysis.** `analyze_word` produces quote, literalness, value shape, substitution shape, field-splitting and pathname behavior, hazards, and multi-field potential. Redirect and substitution facts add `/dev/null` classification, output intent, and syntax. Analysis takes the current `ShellBehaviorAt`.
3. **Safety judgment.** `SafeValueIndex` in `rules/style/unquoted_expansion/` memoizes whether a word or binding is safe in an argv, redirect, numeric-test, pattern, regex, or quoted context. It is rule-private.

Rules consume word facts through `WordFacts` and span helpers in `facts/word_spans/`; they do not re-analyze the AST. Hazard flags include field splitting, pathname matching, tilde expansion, brace fanout, runtime patterns, command or process substitution, and arithmetic expansion.

## Option-sensitive behavior

`ShellBehaviorAt` and the behavior enums in `shuck-semantic` describe field splitting, pathname expansion, glob failure, glob dot matching, glob patterns, array reference policy, subscript indexing, and arithmetic literal interpretation. Fact builders attach the behavior to commands, words, redirects, assignments, case patterns, and arithmetic spans.

The current implementation reports fixed default behavior regardless of the active shell or option state. Raw option-state tracking and per-function option timelines are not implemented, so `setopt`/`shopt` effects and ambiguous option states are not yet modeled. Rule code that matches behavior enums must still handle every variant explicitly.

## Google-style rules

`S078` through `S085` and `C158` through `C161` implement the Google Shell Style Guide checks: shebang policy and form, script size, file description, TODO format, function docs, main entry point, implicit globals, mutable globals, unanchored source paths, and call-before-definition. They are disabled by default, configurable through `[lint.rule-options.<code>]`, and enabled explicitly by code.

The `google` named group still resolves to the older 17-rule ShellCheck-aligned subset, so `--select google` does not enable these rules today. Select them by code, or add the group explicitly with `--extend-select`.
